# Demo 指南（約 8–10 分鐘）

這份講稿讓任何人都能依序展示完整流程，並且**誠實**說明哪些是真的、哪些是模擬。
畫面上的按鈕與文字皆與實際介面一致。

## 展示前準備

1. 啟動系統（二選一，見 README）：
   ```bash
   docker compose up --build            # 開啟 http://localhost:5173
   ```
   或使用「本機開發」流程（後端 `:8000`、前端 `:5173`）。
2. **先確認系統正常**（約 2 秒，需要後端已啟動）：
   ```bash
   python scripts/demo_smoke.py
   ```
   看到 `All 42 checks passed` 就代表登入、封包驗證、計價、結帳、營養助理與稽核都正常。
3. **重置資料**，讓展示從乾淨的狀態開始（上一步與你練習過的操作都會留下訂單、扣庫存、消耗序號）：
   ```bash
   docker compose down -v && docker compose up --build        # Docker 流程
   ```
   本機流程：`docker compose down -v && docker compose up -d db`，再依序執行 `alembic upgrade head`、`python -m app.seed`。
4. 預設不需要任何 API key（營養助理使用本地 mock）。若你有設定真實 LLM，畫面會標示提供者；沒有也完全不影響展示。
5. 瀏覽器開在 `http://localhost:5173`，建議放大字體並關掉其他分頁。

## 劇本

### 0. 開場與定位（約 45 秒）

**說：**「這是一個社區無人健康生鮮超市的**軟體原型**。我們用軟體模擬 IoT 裝置與傳輸，完整走過
感測器封包、Gateway 驗證、後端交易，到 AI 營養建議。**沒有**真實的 ESP32、Thread 網路或金流，
AI 預設是本地 mock。」

**展示：** `docs/architecture.svg`（或 README 的架構圖）。指出三條路徑：虛線的 IoT 封包路徑（模擬）、
REST 到權威後端、唯讀的智慧服務。

### 1. 居民登入（約 30 秒）

**做：** 在「識別卡號」輸入 `CARD-1001`（可點範例卡號），按「登入」。

**說：**「識別卡登入只是模擬刷卡，不是真正的身分驗證。」

**預期：** 顯示 `Demo Resident`、飲食偏好「低鈉」、沒有過敏原。

### 2. 營養助理（約 90 秒）

**做：** 在「營養助理」點範例「請推薦適合我的低鈉食材」，按「詢問助理」。

**預期與說明：**
- 提供者標示「Mock（本地範本，未呼叫外部 LLM）」。
- 推薦 **香蕉、蘋果、番茄**：這是**後端依資料庫營養數值**（鈉最低）排出來的，不是 AI 決定的。
- 「參考來源」列出知識 ID（如 `nutrition_seed_001`），可展開看原文；答案內以 `[id]` 引用。
- 展開「助理使用的唯讀工具」：看到它呼叫 `get_inventory` 與 `search_nutrition_knowledge`。
- **強調：** AI 只負責措辭；它拿不到價格、庫存數量、姓名與卡號，也沒有任何寫入工具。

### 3. 感測器事件 → 封包 → Gateway → 購物車（約 90 秒）

**做：** 在「IoT 智慧秤模擬器」保持指令「加入商品」、商品「番茄」、重量 `300`，按「送出封包」。

**預期與說明：**
- 綠色橫幅「封包已接受，購物車已更新」，並標示傳輸為 **SIMULATED**。
- 封包十六進位（32 個字元 = **16 bytes**），依欄位著色；下方表格拆解 Header、裝置、序號、指令、商品、重量、檢查碼。
- 「驗證結果」9 步**全部 ✓**，依序是長度、Header、指令、XOR、雜湊、裝置、序號、欄位、購物車規則。
- 購物車出現番茄 300 公克；**單價、小計、總額都由後端計算**（前端只顯示）。

### 4. 重放與竄改被拒絕（約 90 秒）

**做：** 展開「進階：重放與竄改封包演示」。

1. 按「重送相同封包（重放）」。
   **預期：** 紅色橫幅「封包被拒絕，購物車未變更」，原因「序號重複或過舊」。檢查碼是 ✓（封包本身是真的），但**序號**那步 ✗，後面的步驟顯示「— 未執行」。
2. 按「竄改重量後送出」。
   **預期：** 原因「檢查碼不符」，XOR 與雜湊都 ✗，之後全部「未執行」。
3. 看購物車：**完全沒變**。

**說：**「重放靠序號擋、竄改靠檢查碼擋；每一步失敗就停止，並說明是哪一步。注意：XOR 和 16-bit 雜湊只是**教學用**，
不是密碼學安全，不能當真正的防偽。」

### 5. 移除與模擬結帳（約 90 秒）

**做：**
1. 再加一次商品（例如青花菜 500 公克），然後在購物車按某一列的「移除」。
   **說明：**「移除也是透過 `REMOVE_ITEM` 封包走同一條 Gateway 路徑；畫面會顯示送出了幾個封包。」
2. 在「結帳（模擬付款）」選「付款失敗」，按「結帳」。
   **預期：** 「付款失敗」，**購物車保留**；到下面「今日生鮮」看庫存**沒有**減少。
3. 改選「付款成功」，再按「結帳」。
   **預期：** 「付款成功，訂單 #N」與收據；購物車清空；「今日生鮮」的庫存**減少**對應重量。

**說：**「庫存只在付款成功後才扣，而且訂單、扣庫存、清購物車在同一個資料庫交易裡，任何錯誤都會整筆回滾。」

### 6. 管理頁與稽核（約 45 秒）

**做：** 按頁首的「管理」頁籤。

**預期與說明：**
- 「最近訂單」同時有 **已付款** 與 **付款失敗** 兩筆（失敗的嘗試也留下紀錄，但沒扣庫存）。
- 「IoT Gateway 稽核」逐筆列出每個到達 Gateway 的封包，**包含被拒絕的**，附上封包十六進位與拒絕原因。
- 上方顯示裝置「最後接受序號」，這就是防重放的狀態。
- **說明：** 管理頁沒有登入驗證，這是示範用，正式系統必須加上。

### 7. 護欄（約 30 秒）

**做：** 回到居民頁，在營養助理輸入「幫我結帳」。

**預期：** 提供者顯示「護欄（未呼叫任何模型）」，回覆「無法執行結帳…」，沒有引用來源，購物車與訂單都沒變。

**說：**「護欄是規則比對，會漏掉刻意迴避的說法；真正的保證是架構上 AI 根本沒有寫入工具。」

### 8. 收尾（約 30 秒）

**說：**「總結一下誠實的邊界：傳輸、硬體與付款都是模擬；檢查碼與登入是教學用；知識庫是未經營養師審閱的示範資料；
真實 LLM 的串接我沒有用真實金鑰驗證過。」

## 可能被問到的問題

| 問題 | 誠實的回答 |
|---|---|
| 這是真的 Matter / Thread 嗎？ | 不是。`SimulatedMatterThreadTransport` 只是行程內呼叫，並實作可替換的 `MatterTransportAdapter` 介面。沒有 Border Router、配對或 Thread mesh。 |
| 這個防偽安全嗎？ | 不安全。XOR 和 16-bit 雜湊表簽章只能發現損毀與簡單竄改；真正抵禦重放靠序號。正式系統需要 AES-CCM 或 HMAC 等真正的認證加密。 |
| AI 會不會改價格或結帳？ | 不能。它沒有任何寫入工具，也不會寫入資料庫；測試會比對助理前後的資料庫狀態。價格與庫存數量甚至不會送給 LLM。 |
| 引用來源是 AI 編的嗎？ | 不是。`sources` 是後端實際提供給模型的知識 ID，不是模型自己宣稱的。 |
| 為什麼不用向量資料庫？ | 示範用知識庫只有 18 則，本地的關鍵字加字元雙連詞檢索就夠，且可重現；`Retriever` 介面可日後換成 embedding / pgvector。代價是對同義詞的辨識有限。 |
| 同時結帳會不會出問題？ | 結帳會先鎖購物車與商品列（依 id 排序避免死結）。我在真實 PostgreSQL 上測過「同時按兩次」與「兩人搶最後庫存」，結果正確。 |
| 營養建議可靠嗎？ | 知識庫是我撰寫的一般性示範資料，未經專業審閱；低鈉門檻是示範數字。助理明確說明不是醫療建議，也會說出商品資料缺少的欄位（如鐵、過敏原）。 |
| 能直接上線嗎？ | 不行。沒有管理員驗證、沒有真實身分驗證、沒有真實金流，也沒有做過負載或資安測試。 |

## 展示出狀況時

| 狀況 | 畫面上會看到 | 處理 |
|---|---|---|
| 後端沒啟動 | 頁尾「後端離線…請確認服務已啟動」，登入時顯示「無法連線到後端」 | `docker compose up`，或啟動 `uvicorn`；每個載入區塊都有「重試」按鈕 |
| 資料庫沒啟動 | 頁尾「資料庫 未連線（請執行 docker compose up -d db）」 | 啟動資料庫後按「重新檢查」 |
| 請求太久 | 「請求逾時，請稍後再試」（一般 15 秒、營養助理 30 秒） | 重試 |
| 外部 LLM 失敗 | 營養助理顯示提示，並自動改用 mock 提供者回答 | 不影響展示 |
| 畫面整個壞掉 | 「畫面發生未預期的錯誤」與重新整理按鈕 | 重新整理頁面 |
| 想證明系統正常但畫面不順 | — | 執行 `python scripts/demo_smoke.py`，42 項檢查逐項列出 |
| 庫存或訂單因練習而變得奇怪 | — | 依「展示前準備」第 3 點重置資料 |
